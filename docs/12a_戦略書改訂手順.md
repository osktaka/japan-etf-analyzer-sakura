# 戦略書改訂手順（target_holdings 更新時）

## 事前チェック

### 1. etfs マスタテーブルに登録済みか確認

```bash
docker compose exec -T backend sqlite3 /app/data/etf.db \
  "SELECT etf_code, name, market_price FROM etfs WHERE etf_code='<新コード>';"
```

未登録なら以下のいずれかで登録:
- `sync_etf_from_jpx.py` を実行（JPX公式リストから一括同期）
- 管理画面（admin）から手動登録

### 2. price_histories に直近データが入っているか確認

```bash
docker compose exec -T backend sqlite3 /app/data/etf.db \
  "SELECT date, close FROM price_histories WHERE etf_code='<新コード>' ORDER BY date DESC LIMIT 3;"
```

未取得なら:

```bash
docker compose exec -T backend python3 scripts/update_etf_data.py --smart --rate-limit 3.0
```

## 既知の落とし穴（過去事例）

### 2026-05-14: portfolio_rebalance_service の構造バグ

A群に 1547 S&P500 を新規追加した際、`portfolio_rebalance_service.py` の構造バグにより、保有ゼロ採用銘柄の `current_price` が `0.0` 固定となり、買付プランから完全脱落した。

**症状**:
- 採用銘柄配分テーブルには出る（CRITICAL状態）
- しかし「主な買付候補」「売買プラン詳細表」には出ない

**修正済み**: `current_price = 0.0` の場合はETFマスタの `market_price` をフォールバック取得するように変更（2026-05-14対応）。`backend/src/services/portfolio_rebalance_service.py` の `calculate_rebalance_plan()` 参照。

### A群×B群の銘柄重複時の按分対応

A群に追加する銘柄が既にB群にある（または逆）場合、ポートフォリオ全体での集中度が膨らむ。

**対応パターン**:
1. 移動元から銘柄を削除し、残りの銘柄を按分で再配分（例: 2026-05-15 改訂で 1629 商社を A群15% に移動し B群を 4銘柄×11.25% に按分）
2. 移動元に別銘柄を追加して構成を維持（例: 2026-05-16 で 200A 半導体を B群9% で新規追加し B群を 5銘柄×9% に再構成）

戦略書 §1 で反省した「単一業種への集中ベット」を避けるため、A×B 重複は必ず解消する。
