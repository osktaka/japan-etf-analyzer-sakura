# 銘柄評価設計（etf-rating スキル）

## 概要

`/etf-rating` スキルは、個別 ETF 銘柄について「銘柄ごとにカスタム
した上昇10条件 × 下落10条件」を現在の市場情勢にマッチさせて
0〜100 点で採点し、Top5ドライバー重み×2 を適用してネット中期スコア
（中立=100、上限=200）・先取り/後追い区分・3シナリオまで一気通貫で
出力するプロジェクトスキル。

2026-05-22 に手作業で実施した 1629（NEXT FUNDS 商社・卸売）の中期
マッチ度評価レポート（`reports/research/1629_evaluation_20260522.md`）
の評価フレームを汎用化・自動化したもの。

### 目的と棲み分け

| スキル | 焦点 | 主要出力 |
|--------|------|----------|
| `/etf-rating` | **個別銘柄 × 現在情勢のマッチ度**（中期 3〜12ヶ月） | 銘柄別レポート + 1通メール |
| `/my-portfolio` | test ユーザーの保有・配分・乖離 | 損益/配分プレビュー |
| `/pf-v2` | ポートフォリオ全体のリスク・分散・品質 | 総合分析レポート |
| `/market-outlook-v2` | 当日の東証見通し・振り返り | 朝/夕レポート |

「個別銘柄が今この瞬間に追い風か逆風か」だけを判定する責務。
ポートフォリオ全体の最適化や東証マクロ見通しは別スキルが担う。

### スキル起動方法

```bash
# 単一銘柄評価（メール送信なし、手動検証用）
/etf-rating 1629

# target_holdings 全銘柄 + watchlist を順次評価（メール送信なし）
/etf-rating all

# 全銘柄評価 + メール送信（cron 自動実行はこの形）
/etf-rating all --send-mail

# 観点（criteria YAML）の見直し対話
/etf-rating tune 1629
```

cron からは平日（月-木 18:00 / 金 18:15）に `scripts/cron-etf-rating-daily.sh` 経由で
`/etf-rating all --send-mail` が起動される（[`10_バッチ処理設計.md`](10_バッチ処理設計.md) 参照）。

## 評価フレーム詳細

### 上昇10項目・下落10項目の構造

各銘柄について **上昇条件 A-1〜A-10**（10項目固定）と
**下落条件 B-1〜B-10**（10項目固定）を設計する。条件は銘柄特性
（セクター・利益構造・為替/金利感応度・分配金特性等）に応じて
個別にカスタムする。

| 項目 | 上昇条件（A群） | 下落条件（B群） |
|------|----------------|-----------------|
| 項目数 | 10 固定 | 10 固定 |
| 採番 | A-1, A-2, ..., A-10 | B-1, B-2, ..., B-10 |
| スコア意味 | 高得点 = 強い追い風 | 高得点 = リスク大 |
| データ参照 | Phase 0 市場スナップショット（共通） + 個別 WebSearch | 同左 |

### 0-100 スコアリング方式

| 帯 | スコア | 意味（上昇条件） | 意味（下落条件） |
|----|--------|--------------------|------------------|
| 強気 | 90-100 | 完全マッチ | 重大リスク顕在化 |
| 強い追い風 / 警戒 | 70-89 | 強い追い風 | 重大リスク（要注意マーク） |
| やや追い風 / やや警戒 | 60-69 | やや追い風 | やや警戒 |
| **中立** | **50** | **判断保留** | **判断保留** |
| やや逆風 / 低リスク | 30-49 | やや逆風 | リスク低 |
| 強い逆風 / 安全 | 0-29 | 強い逆風 | 安全 |

しきい値は `calc_params.json` の `scoring.strong_bullish_threshold = 70`
および `scoring.warning_threshold = 70` で SSOT 管理。

### 判定ラベル基準（メール本文の表示用）

メール本文（[`06b_メール通知仕様.md`](06b_メール通知仕様.md) 参照）では、
`net_score` を以下の帯で 5 段階の判定ラベルに変換して表示する。
ラベルは `backend/src/services/templates/etf_rating/_macros.j2` の
`verdict_parts(score)` マクロで管理。

| 総合点（`net_score`） | ラベル | 絵文字 | HTML バッジ色（背景／文字） |
|---|---|---|---|
| 70 以上 | 強い追い風 | 🟢 | #e8f5ec / #1b7f3a |
| 60〜69 | 追い風 | 🟢 | #f0f7e8 / #3a7d1b |
| 40〜59 | 中立寄り | 🟡 | #fff8e1 / #8a6a00 |
| 30〜39 | 警戒 | 🔴 | #fef0e6 / #a85400 |
| 30 未満 | 重大警戒 | 🔴 | #fdecec / #c0392b |

しきい値の根拠:

- **70**: `calc_params.json` の `scoring.strong_bullish_threshold` と一致。
  上昇条件スコア70点以上を「強い追い風」と定義する内部基準を、総合点側にも同じ閾値で適用
- **30**: `calc_params.json` の対称下限。上昇条件30点未満を「条件不成立」と
  みなす内部基準を総合点に適用し「警戒」とする
- **60 / 40**: 70 と 30 の中点（中立=50）から ±10 オフセット。
  「明確な追い風／中立寄り／警戒」の3区分を視覚的に出すための補助境界

なお件名側の集計（"強い追い風 K銘柄" / "警戒 W銘柄"）は **`payload.flags`
リストの `type` 値**（`strong_tailwind` / `severe_risk` 等）でカウントし、
本表のラベルとは独立に決まる（Phase 1 / Phase 2 で個別銘柄ごとに判定して
flags に格納する）。両者は通常一致するが、`net_score` ベースの判定と
`upside_weighted` 単独ベースの判定で乖離が出ることもあるため、件名と
表内ラベルが微妙にずれる可能性がある点に注意する。

### 先取り（leading）/ 後追い（lagging）/ 混在（mixed）の区分

各条件には `type` フィールドで時間軸属性を付与する。

| type | 意味 | 活用 |
|------|------|------|
| `leading` | 先取り（今後 3〜12ヶ月でこれから効く） | 次の波を読むシグナル |
| `lagging` | 後追い（既に株価に織り込み済み） | 現状認識と過熱判定 |
| `mixed` | 先取り＋後追い混在 | グレーゾーン |

サマリでは `leading_net` / `lagging_net` を分けて集計し、
「先取りスコア > 後追いスコア」なら **これから動くフェーズ** と判定する。

### Top5 ドライバー重み×2

各銘柄の YAML で **Top5 ドライバー（上昇）** と
**Top5 リスクドライバー（下落）** を ID で指定する。重み係数は以下:

| 区分 | 重み |
|------|------|
| Top5 ドライバー / リスクドライバー | **×2.0** |
| その他の条件 | ×1.0 |

ソース: `calc_params.json` の `weights.top5_multiplier = 2.0`。
1629 評価レポート（`reports/research/1629_evaluation_20260522.md`）の
採点ルールを踏襲。

### ネット中期スコア

```
upside_weighted   = Σ(score_i × weight_i) / Σ(weight_i)   ※上昇10条件
downside_weighted = Σ(score_j × weight_j) / Σ(weight_j)   ※下落10条件

net_score = upside_weighted + (100 − downside_weighted)
```

| 値 | 意味 |
|----|------|
| 100 | 中立（追い風と逆風が拮抗） |
| 130-150 | 中期的に追い風優勢 |
| 150-180 | 強い追い風（保有/買い増し検討） |
| 180-200 | 完全マッチ（極端な上振れ条件） |
| 70-100 | 逆風優勢（縮小/様子見） |
| <70 | 強い逆風（売却検討） |

ソース: `calc_params.json` の `net_score.formula` および `net_score.neutral = 100`。

### 3シナリオ（基本/上振れ/下振れ）の枠組み

各銘柄の YAML で `scenarios.{base, upside, downside}` 3本を必須定義する。

| シナリオ | 説明 | 期待リターン例（1629） |
|---------|------|----------------------|
| `base` | 現状条件が続く維持シナリオ（3〜12ヶ月の中期前提） | +10〜+20% |
| `upside` | 追い風条件が複数強化される上振れ | +25〜+40% |
| `downside` | リスク条件が複数顕在化する下振れ | -20〜-30% |

オプションで `upside_extreme` / `downside_extreme`（Top5 が 2 つ以上同時加速/顕在化する極端ケース）も追加可能。
詳細は `calc_params.json` の `scenario_definitions` 参照。

### 条件ブロックのスキーマ

```yaml
- id: "A-1"                          # 必須・A-N または B-N
  description: "条件の簡潔な説明"     # 25字程度推奨
  type: "leading"                     # leading | lagging | mixed

    指標名:
      strong_bullish: ">=90"
      bullish: ">=70"

  past_cases:
    - "YYYY-MM イベント名"
```

下落条件は `strong_bullish` の代わりに `strong_bearish`（高スコア=リスク大）を使う点に注意。

## スコアキャリブレーション基準

LLM 採点ブレを抑えるため、しきい値は **数値で明示** することを必須とする。

### キャリブレーション例（数値指標がある場合）

| 指標 | 90点（強気） | 70点（追い風） | 50点（中立） | 30点（逆風） |
|------|-------------|---------------|-------------|------------|
| 配当利回り | ≥6% | 4-6% | 3-4% | <3% |
| PBR | <0.7 | 0.7-1.0 | 1.0-1.5 | ≥1.5 |
| ドル円（円安銘柄向け） | ≥155 | 150-155 | 145-150 | <145 |
| VIX（リスクオン銘柄向け） | <13 | 13-16 | 16-20 | ≥20 |

### 定性指標の場合

「業界アナリスト推奨が多数」「需給逼迫の報道が継続」など定性的な
場合も、`thresholds.indicator_name.{strong_bullish, bullish, neutral, bearish}`
に **判定の根拠キーワード** を1行で記述する。

### 変動ガード

`calc_params.json` の `drift_alert`:

| パラメータ | 値 | 用途 |
|-----------|-----|------|
| `score_change_pp_threshold` | 5 | 前日比±5pp 超でサマリ「ハイライト」対象 |
| `score_change_pp_strong_threshold` | 15 | 前日比±15pp 超で**変動理由の明記を必須化**（LLM ブレ抑制） |
| `criteria_version_age_yellow_days` | 90 | criteria YAML 90日経過で黄色警告 |
| `criteria_version_age_red_days` | 180 | 同180日経過で赤色警告 |

## 観点追加・改訂手順

### 新銘柄追加時のフロー（watchlist 拡張）

1. **テンプレ複製**: `cp .claude/skills/etf-rating/criteria/_template.yaml .claude/skills/etf-rating/criteria/{code}.yaml`
2. **基本情報入力**: `code` / `name` / `sector` / `benchmark_index` / `notes` を埋める
3. **上昇10条件設計**: セクター特性・利益構造から A-1〜A-10 を起票（先取り3-5、後追い3-5、混在1-2）
4. **下落10条件設計**: 同様に B-1〜B-10 を起票（過去の急落事例から逆算すると漏れにくい）
5. **Top5指定**: `top5_drivers` / `top5_risk_drivers` を選定（×2 重みの効果を試算）
6. **3シナリオ記述**: base / upside / downside の期待リターンレンジを明記
7. **初回採点で検証**: `/etf-rating {code}` で実行し、ネットスコアが妥当か確認
8. **回帰確認**: 既存銘柄のネットスコアが前日比±5pp 以内か（無関係な銘柄に影響していないか）

### 週次 tune の運用ルール

毎週1回（金曜18:00 以降を推奨）、スコアボラティリティの高い銘柄を抽出して観点を見直す:

```bash
# 観点見直し対話を起動
/etf-rating tune 1629
```

- 直近30日の `data/etf-rating/history/{code}.jsonl` を読み込み、スコアの
  ボラティリティ・条件別寄与の偏りを集計
- 提案ベースで `AskUserQuestion` を順次表示（追加/削除/閾値調整）
- 承認後、YAML の `revision_history` に追記 + `version` を更新

**改訂対象になりやすいパターン**:
- 同じ条件が常に 50（判断保留）→ しきい値を緩めるか削除
- 前日比±15pp 超が3日連続 → しきい値が市場感度と合っていない
- 90日経過 → 鮮度警告（黄）が出るので強制的に見直し対象

### revision_history 記載方針

```yaml
revision_history:
  - date: "2026-05-22"
    note: "初版"
  - date: "2026-06-15"
    note: "A-3 円安しきい値を150→155に更新（介入水準引き上げ反映）"
  - date: "2026-07-08"
    note: "B-7 削除（中国経済指標は B-2 と重複）。Top5 リスクから B-7 を除外"
```

- 日付は YYYY-MM-DD、note は何をなぜ変えたかを 1〜2 行で
- 削除した条件 ID は再利用しない（追跡のため）
- version は `YYYY-MM-DD_vN` で同日複数改訂時のみ `N` をインクリメント

## 採点履歴 jsonl 仕様

保存先: `data/etf-rating/history/{code}.jsonl`（1日1行追記）

### 1行のスキーマ（11フィールド）

```json
{
  "date": "20260522",
  "code": "1629",
  "net_score": 167.4,
  "upside_weighted": 71.9,
  "downside_weighted": 37.2,
  "leading_net": 28.0,
  "lagging_net": 37.0,
  "upside_avg": 70.9,
  "downside_avg": 35.8,
  "criteria_version": "2026-05-22_v1",
  "criteria_age_days": 0
}
```

| フィールド | 型 | 意味 |
|------------|-----|------|
| `date` | str (YYYYMMDD) | 評価実行日（JST） |
| `code` | str | ETF コード |
| `net_score` | float | ネット中期スコア（中立=100、上限=200） |
| `upside_weighted` | float | 上昇加重スコア（0-100、Top5×2 適用） |
| `downside_weighted` | float | 下落加重スコア（0-100、Top5×2 適用、高いほどリスク大） |
| `leading_net` | float | 先取り条件のみのネット |
| `lagging_net` | float | 後追い条件のみのネット |
| `upside_avg` | float | 上昇単純平均（重み無し、Σ(A-1〜A-10)/10） |
| `downside_avg` | float | 下落単純平均（重み無し、Σ(B-1〜B-10)/10） |
| `criteria_version` | str | 使用した criteria YAML の version |
| `criteria_age_days` | int | criteria 改訂からの経過日数（鮮度監視用） |

### 利用法

- **前日比算出**: 当日と直近営業日の `net_score` 差を `delta` として表示
- **ボラティリティ算出**: tune コマンドで直近30日の標準偏差を計算
- **観点鮮度監視**: `criteria_version` の日付から経過日数を算出（90日=黄、180日=赤）
- **回帰検出**: criteria 改訂直後にネットスコアが大きくジャンプしていないか確認

## メール通知

平日（月-木 18:00 / 金 18:15）に終値ベースで全銘柄評価を 1 通のメールで配信する。金曜のみ 18:15 にずらすのは daily_advisor_weekly (18:00) との並列を避けるため。
仕様詳細は [`06b_メール通知仕様.md`](06b_メール通知仕様.md) の「ETF Rating 通知（終値ベース日次）」章を参照。

- 件名フォーマット: `[M/D ETF-Rating] N=X 平均Y 強N1警N2`（40字以内）
- 本文構成: 総評・ランキング・ハイライト・観点鮮度警告・銘柄別フル詳細（`<details>` 折りたたみ）・データソース・フッタ
- HTML サイズ上限: 100KB（超過時は自動縮約）
- 環境変数 `ETF_RATING_MAIL_ENABLED=1` で送信有効化（既定: 無効）

## 株価計算の必須ルール

CLAUDE.md「株式分割の管理」セクションを厳守すること:

3. 対象銘柄の `stock_splits` を事前確認（`is_applied` / `is_chart_applied`）

## 履歴永続化方針

`data/etf-rating/history/{code}.jsonl` は前日比算出・ボラティリティ算出・観点鮮度監視の SSOT として継続的に追記される。データ消失は前日比やボラ計算の精度を直接損なうため、環境別に方針を分ける。

### 開発環境

- **git 管理外**（`.gitignore` に `data/etf-rating/` を登録済み）
- ホスト永続ボリューム（プロジェクトディレクトリ直下）に直接書き出す
- Docker コンテナ削除でも消えない（バインドマウント運用）
- バックアップ不要（再生成可能・検証目的）

### 本番環境（さくらレンタルサーバー）

- **暫定方針**: 月1回手動 `tar.gz` 化して `data/backups/` 配下に退避（`migrate.sh` のバックアップ運用と同じディレクトリに集約）
- **将来検討**: SQLite テーブル化（`etf_rating_history` テーブル）への移行
  - 利点: `batch_logs` 等と同様に DB マイグレーション・バックアップ機構に統合可能、jq 不要で集計クエリが書ける
  - 欠点: スキル側が SQLite 直接書込にアクセスするため、Phase 1 のシェル組立が複雑化
- **判断時期**: 本番デプロイ時に再評価（YAGNI のため Phase A では jsonl 継続）
