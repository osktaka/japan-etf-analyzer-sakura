# バッチ処理設計

## 1. 概要

ETFデータの自動更新・メンテナンスを行うバッチ処理群の設計。cronによるスケジュール実行と、障害時の自動リトライ機構を備える。

## 2. 共通基盤（BaseBatchScript）

すべてのバッチスクリプトは `backend/scripts/base_batch.py` の `BaseBatchScript` を継承する。

### 提供機能

| 機能 | 説明 | 設定 |
|------|------|------|
| Flask app context管理 | DB接続・モデル利用を自動化 | 常時有効 |
| バッチログ記録 | `batch_logs` テーブルに実行記録を保存 | `enable_batch_log` |
| 進捗追跡 | 処理済み件数・最終処理コードを記録 | `enable_progress` |
| レジューム機能 | `--resume BATCH_LOG_ID` で失敗箇所から再開 | `enable_resume` |
| dry-runモード | `--dry-run` で変更なしに実行内容を確認 | 常時有効 |

### クラス構成

- **`BaseBatchScript`** - フル機能の基底クラス（バッチログ・進捗・レジューム対応）
- **`SimpleBatchScript`** - バッチログなしの軽量版（batch_monitor用）

## 4. スケジュール（crontab）

タイムゾーン: Asia/Tokyo

| 時刻 | 曜日 | スクリプト | 備考 |
|------|------|-----------|------|
| 06:00 | 月曜 | `sync_etf_from_jpx.py` + `update_scores.py` | 銘柄マスター更新後にスコア再計算 |
| 19:00 | 平日 | `update_etf_data.py --smart --rate-limit 3.0` | 市場閉場後に株価データ取得 |
| 20:30 | 平日 | `sync_dividend_from_minkabu.py --rate-limit 1.5` + `update_scores.py` | 配当データ更新後にスコア再計算 |
| 02:00 | 日曜 | `sync_historical_splits.py --all --rate-limit 5.0` | 週次で分割履歴を同期 |
| 05:00 | 日曜 | `rotate_logs.py` | ログローテーション |
| */5 | 毎日 | `batch_monitor.py` | 5分間隔で監視・自動リトライ |

## 5. 依存関係

```
sync_etf_from_jpx.py ──→ update_scores.py
  (銘柄マスター更新)        (スコア再計算)

update_etf_data.py ──→ update_scores.py
  (株価取得)               (スコア再計算・勢い履歴保存)
  ├─ performance_cache 更新 ─→ regression_rate (1m, 3m) を参照
  └─ momentum_label 更新

sync_dividend_from_minkabu.py ──→ update_scores.py
  (配当利回り更新)                  (スコア再計算)
```

### 依存ルール

- `update_scores.py` は `performance_cache` テーブルの `return_rate`・`volatility` および `regression_rate`（1m, 3m）を参照するため、`update_etf_data.py` の後に実行する
- `update_scores.py` は配当利回り（`etfs.dividend_yield`）を参照するため、`sync_dividend_from_minkabu.py` の後に実行する
- crontabのスケジュールで実行順序を担保（19:00 → 20:30）

## 6. ログ管理

### ログファイル

| ファイル | 出力元 |
|---------|--------|
| `logs/master_sync.log` | `sync_etf_from_jpx.py` |
| `logs/etf_update.log` | `update_etf_data.py` |
| `logs/dividend_update.log` | `sync_dividend_from_minkabu.py` |
| `logs/score_update.log` | `update_scores.py` |
| `logs/split_sync.log` | `sync_historical_splits.py` |
| `logs/rotate.log` | `rotate_logs.py` |
| `logs/batch_monitor.log` | `batch_monitor.py` |

### ローテーションポリシー

- `rotate_logs.py` が毎週日曜 05:00 に実行
- 10MB超のログファイルをローテーション（最大5世代保持）
- 90日超の古いログを自動削除
- DBの `batch_logs` レコードも90日超で削除

## 7. 障害時対応

### 自動リトライ（batch_monitor）

`batch_monitor.py` が5分間隔で以下を実行:

1. **タイムアウト検知**: 10分以上ハートビート更新がない `running` ジョブを `failed` に更新
2. **自動リトライ**: 直近5-60分で `failed` になったジョブを `--resume` 付きで再実行
3. **リトライ上限**: 最大3回まで（`retry_count >= 3` でスキップ）

### リトライ対象バッチ

| バッチ名 | resume機能 | リトライ時オプション |
|---------|-----------|-------------------|
| `update_etf_data` | あり（途中再開） | `--smart --rate-limit 3.0 --resume ID` |
| `update_scores` | あり（途中再開） | `--resume ID` |
| `sync_etf_from_jpx` | あり（最初から再実行） | `--resume ID` |

### 手動対応

バッチが繰り返し失敗する場合:

```bash
# ログを確認
tail -100 logs/etf_update.log

# 手動で再実行（本番環境）
cd ~/www/japan-etf-analyzer
source backend/venv/bin/activate
python backend/scripts/update_etf_data.py --smart --rate-limit 3.0

# dry-runで事前確認
python backend/scripts/update_etf_data.py --smart --dry-run
```
