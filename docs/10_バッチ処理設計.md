# バッチ処理設計

## 1. 概要

ETFデータの自動更新・メンテナンスを行うバッチ処理群の設計。cronによるスケジュール実行と、障害時の自動リトライ機構を備える。

## 2. 共通基盤（BaseBatchScript）

すべてのバッチスクリプトは `backend/scripts/base_batch.py` の `BaseBatchScript` を継承する。

### 提供機能

| 機能 | 説明 | 設定 |
|------|------|------|
| Flask app context管理 | DB接続・モデル利用を自動化 | 常時有効 |
| バッチログ記録 | `batch_logs` テーブルに実行記録を保存 | `enable_batch_log` |
| 進捗追跡 | 処理済み件数・最終処理コードを記録 | `enable_progress` |
| レジューム機能 | `--resume BATCH_LOG_ID` で失敗箇所から再開 | `enable_resume` |
| 依存チェック | 依存バッチの完了を確認してから実行 | `depends_on` / `check_window` |
| dry-runモード | `--dry-run` で変更なしに実行内容を確認 | 常時有効 |

### クラス構成

- **`BaseBatchScript`** - フル機能の基底クラス（バッチログ・進捗・レジューム対応）
- **`SimpleBatchScript`** - バッチログなしの軽量版（batch_monitor用）

## 4. スケジュール（cron-batch.sh ディスパッチャ）

タイムゾーン: Asia/Tokyo

開発環境では **ホストcron + `scripts/cron-batch.sh`** で全ジョブを集約管理する（schedulerコンテナは2026-04-29に廃止）。ホストcronは1エントリのみ:

```cron
*/5 * * * * /path/to/japan-etf-analyzer-sakura/scripts/cron-batch.sh >> /path/to/japan-etf-analyzer-sakura/logs/cron-batch.log 2>&1
```

スクリプト内部で時刻・曜日・祝日判定を行い、該当ジョブを `docker compose exec -T backend python3 scripts/<NAME>.py` で起動する。各バッチは `flock`（`/tmp/cron-batch-<NAME>.lock`）で多重起動防止、バックグラウンド並列実行（チェーン実行時のみ同期 fail-stop）。

### 環境プロファイル

`CRON_BATCH_PROFILE=dev|prod`（デフォルト `dev`）で実行ジョブを切替える。不正値は `exit 2` で起動拒否。本番（さくら）デプロイ時は `prod` に設定し、開発専用ジョブ（advisor 4本＋theme_etfs＋mechanical_rule_watcher）を自動的に除外する。

## 5. 依存関係

```
sync_etf_from_jpx.py ──→ update_scores.py
  (銘柄マスター更新)        (スコア再計算)

update_etf_data.py ──→ update_scores.py
  (株価取得)               (スコア再計算・勢い履歴保存)
  ├─ performance_cache 更新 ─→ regression_rate, return_rate (各全8期間) を参照
  └─ momentum_label 更新

sync_from_minkabu.py ──→ update_scores.py
  (配当利回り・純資産額更新)        (スコア再計算)
```

### 依存ルール

- `update_scores.py` は `performance_cache` テーブルの `return_rate`・`volatility` および `regression_rate`（全8期間: 1m, 3m, 6m, 1y, 3y, 5y, 10y, 20y）を参照するため、`update_etf_data.py` の後に実行する
- `update_scores.py` は配当利回り（`etfs.dividend_yield`）を参照するため、`sync_from_minkabu.py` の後に実行する
- `update_scores.py` は営業日判定を内蔵（`jpholiday`で祝日、`weekday()`で土日を判定）し、非営業日はバッチログを作成せずスキップする。これにより祝日に不要な `etf_metrics_history` レコードが作成されることを防止する

### 依存チェック機能

`BaseBatchScript` のクラス属性 `depends_on` と `check_window` により、依存バッチの完了を自動チェックする仕組み。従来のスケジュール順序（schedulerコンテナ内cron）による暗黙的な担保に代わり、明示的な依存チェックで実行順序を保証する。

#### クラス属性

| 属性 | 型 | 説明 |
|------|-----|------|
| `depends_on` | `list[str]` | 依存するバッチ名のリスト（例: `["update_etf_data", "sync_from_minkabu"]`） |
| `check_window` | `tuple[str, str]` | 依存チェックを行う時間帯（JST）。例: `("16:30", "22:00")` で16:30〜22:00の範囲外はスキップ |

#### チェックフロー

1. **時間帯判定**: 現在時刻（JST）が `check_window` の範囲外ならスキップ
2. **依存完了確認**: `depends_on` の全バッチが今日（JST）成功しているか確認。未完了ならスキップ（次のcron周期で再チェック）
3. **自バッチ未成功判定**: 自バッチが今日まだ成功していなければ実行（初回実行）
4. **依存バッチ時刻比較**: 依存バッチの最新成功時刻（`finished_at`）のいずれかが自バッチの最新成功時刻より新しければ実行（新データあり）。すべて自バッチより古ければスキップ（処理済み）

#### バイパス条件

以下の場合、依存チェックは自動的にスキップされる:

- **`--skip-dep-check`**: 依存チェックを明示的にスキップ。月曜cronのように `sync_etf_from_jpx.py` とチェーン実行する場合に使用（直前のバッチ完了が保証されているため）
- **`--resume`**: 失敗したバッチの途中再開時。依存バッチは前回実行時に既に完了しているため再チェック不要

## 7. 障害時対応

### 自動リトライ（batch_monitor）

`batch_monitor.py` が5分間隔で以下を実行:

1. **タイムアウト検知**: 10分以上ハートビート更新がない `running` ジョブを `failed` に更新
2. **自動リトライ**: 直近5-60分で `failed` になったジョブを `--resume` 付きで再実行
3. **リトライ上限**: 最大3回まで（`retry_count >= 3` でスキップ）

### リトライ対象バッチ

| バッチ名 | resume機能 | リトライ時オプション |
|---------|-----------|-------------------|
| `update_etf_data` | あり（途中再開） | `--smart --rate-limit 3.0 --resume ID` |
| `update_scores` | あり（途中再開） | `--resume ID`（依存チェック自動スキップ） |
| `sync_etf_from_jpx` | あり（最初から再実行） | `--resume ID` |

### 全件失敗の検知（status の補正）

ネットワーク断などで「処理を起動できたがすべての個別アイテムが失敗した」ケースを `status='success'` のまま記録すると、`has_succeeded_today.py` が当日成功と誤判定し、catch-up 機構でも救えなくなる。これを防ぐため `BaseBatchScript._finish_batch_log` に**全件失敗ガード**を実装している。

**判定ロジック**:

| 条件 | status |
|------|--------|
| 呼び出し側が `success=False` を指定 | `failed`（変更なし） |
| `total_count > 0` かつ `success_count == 0` | `failed`（**強制補正**） |
| それ以外（部分成功含む） | `success`（呼び出し側の指定どおり） |

**仕様**:

- 呼び出し側（個別バッチ）が `_finish_batch_log(success=True, success_count=N, total_count=M)` を渡したときのみ判定が走る
- `success_count` / `total_count` を渡さない場合は従来挙動を維持（例: `daily_advisor_*` は処理件数概念がないため対象外）
- 部分成功（例: 206/454）は `success` のまま維持し、誤検知を避ける
- 全件失敗時は `error_message` に "All N items failed (0 success). Marking batch as failed." が記録される

**対象バッチ**:

| バッチ名 | 全件失敗ガード | 備考 |
|---------|--------------|------|
| `sync_from_minkabu` | あり | 0/N でDNS失敗時など |
| `update_etf_data` | あり | `success + skipped` を成功扱い |
| その他 | なし | 処理件数概念がないか、個別レポートで十分 |

**設計判断**:

- `BaseBatchScript` 経由のオプトイン方式を採用（個別バッチが `success_count` / `total_count` を明示的に渡したときだけ判定）
- 既存呼び出し（引数なし）は完全に挙動が維持されるため、advisor 系など処理件数概念のないバッチへの影響なし
- 「処理件数 > 0 かつ 成功件数 = 0」という閾値のみで判定。部分成功は健全とみなし誤検知を避ける（YAGNI）

### 依存チェックと障害時の挙動

- **`--resume` 時**: 依存チェックは自動的にバイパスされる。前回実行時に依存が充足されていたため、再チェックは不要
- **`--skip-dep-check` 時**: 月曜cronのようにチェーン実行（`&&`）で直前バッチの成功が保証される場合に使用。依存チェックを明示的にスキップする
- **依存未充足による未実行**: `update_scores.py` は10分間隔で依存チェックを行うため、依存バッチの完了後に自動的に実行される。依存バッチが失敗し続ける場合は `batch_monitor.py` が依存バッチのリトライを行い、成功後の次のcron周期で `update_scores.py` が実行される

### 当日キャッチアップ機構

`batch_monitor` は「**発火後に失敗したジョブ**」を3回までリトライするが、マシン停止やネットワーク断で「**発火そのものを逃したジョブ**」はカバーしない。この穴を埋めるのが **当日キャッチアップ機構** である。

#### アーキテクチャ: pull型 sweep

```
*/5 host cron → cron-batch.sh
                 ├─ 既存: 時刻ピッタリの dispatch（無変更）
                 └─ 新規: catch_up_sweep（末尾で1回）
                       → CATCHUP_JOBS の各エントリを評価し発火可否を判定
```

cron-batch.sh の `catch_up_sweep` 関数が `CATCHUP_JOBS` 配列（バッチ名・sched・until・曜日・プロファイル）を順に評価し、以下の全条件を満たすバッチを発火する:

1. 現在時刻が `sched` を**超過**（=ピッタリは通常 dispatch に委譲・重複防止）し、`until` 以下
2. 曜日条件OK（weekday / daily / mon / fri / sun）
3. 祝日OK（既存 dispatch と整合: 平日対象は祝日スキップ、月曜マスタチェーンと金曜weeklyは祝日でも実行）
4. プロファイル一致（`CRON_BATCH_PROFILE` = dev/prod、または both）
5. `backend/scripts/has_succeeded_today.py NAME` が exit 1 を返す（当日まだ成功記録なし）

#### 設計判断

| 論点 | 採用 | 理由 |
|------|------|------|
| 連鎖の扱い | **次の */5 サイクルに委ねる**（fixed-point ループなし） | 前提バッチ完了 → 5分後 sweep で後続が条件を満たし発火。当日中なら最大5分遅延は許容。実装単純化（YAGNI） |
| 遡り範囲 | 当日のみ（JST 0:00-23:59） | `get_latest_success_time` の参照基準が JST 0:00 リセットなので自然な実装。翌日持ち越しは別問題なので分離 |
| 高頻度バッチ（*/5・*/10） | catch-up 対象外 | 短期サイクル内で自然リカバリされる。catch-up 不要 |
| 通知系の窓 | `until` 超過でスキップ | 古い情報を朝7時用テンプレで送ると害になるため、時間帯を過ぎたら諦める方針 |
| アーキテクチャ | pull 型 sweep | push 型（バッチごとに発火タイマー）と比べ、起動経路が一本化されデバッグ容易 |

| `sync_from_minkabu` | 16:00 | 22:00 | 平日（祝日スキップ） | both | — |

**対象外と理由**:

| 対象外バッチ | 理由 |
|------------|------|
| `batch_monitor`（*/5） | 高頻度。短期サイクル内で自然リカバリ |
| `update_scores`（*/10 16-20） | 同上。16:00〜20:00 で10分おきに何度も発火 |
| `mechanical_rule_watcher`（*/5 9-15） | 同上。場中5分おきに発火 |
| `sync_etf_from_jpx` | 月曜マスタチェーン1段目。`run_chain` 同期実行が前提のため個別 catch-up は不適 |
| `update_scores_master` | 同2段目。実体 `update_scores.py` の `check_window=(16:30, 22:00)` により午前帯発火がほぼ skip される。また `batch_logs.name` は `update_scores` で記録されるため `update_scores_master` 名での「当日成功記録」判定が常に未成功扱いとなり、毎サイクル発火試行が発生する |
| `sync_historical_splits` | 同3段目。`depends_on` を持たないため、`sync_etf_from_jpx` 未完了でも並列発火するリスクあり |

月曜マスタチェーン障害時は **手動運用**で対応する:

```bash
# 個別に順次再実行（直前バッチ完了を確認しながら）
bash scripts/cron-batch.sh --only sync_etf_from_jpx
bash scripts/cron-batch.sh --only update_scores_master
bash scripts/cron-batch.sh --only sync_historical_splits
```

#### 自己防衛

catch-up sweep が無条件で起動しても、各バッチ側で安全に止まる:

- `BaseBatchScript._check_dependencies()`: `depends_on` の前提未充足なら exit 0（skip）で終了。catch-up が暴走しても二重起動・データ破壊は起きない
- `flock`（`/tmp/cron-batch-<NAME>.lock`）: 通常 dispatch との同時起動を防止
- `has_succeeded_today.py` が exit 2（エラー）を返す場合は安全側に倒して catch-up 対象外とする

#### 重複防止

`should_catchup` の時刻判定は **`sched < now`**（厳密超過）で行うため、sched ピッタリの発火（例: 16:00）は通常 dispatch が独占的に拾う。catch-up は16:05以降から候補に上がる。

#### 検証方法

```bash
# 16:00を逃した想定（19:00時点）
bash scripts/cron-batch.sh --at 19:00 --dow 3 --dry-run
# 期待: update_etf_data, sync_from_minkabu, daily_advisor_evening が CATCHUP 候補

# 朝のmorning窓外スキップ
bash scripts/cron-batch.sh --at 10:00 --dow 3 --dry-run
# 期待: daily_advisor_morning は窓外（until=09:00 超過）で対象外

# 月曜マスタチェーンは catch-up 対象外
bash scripts/cron-batch.sh --at 12:00 --dow 1 --dry-run
# 期待: マスタチェーン3バッチは CATCHUP 候補に現れない（rotate_logs のみ）

# 単一バッチの当日成功有無を確認
docker compose exec -T backend python3 scripts/has_succeeded_today.py update_etf_data
# 0=成功済 / 1=未成功 / 2=エラー
```
